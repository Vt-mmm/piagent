# Harness Next: production API families and nested identity

Status: development implementation and qualification; not an independent release evaluation.

## Evidence-driven change

The async worker could execute retry/checkpoint APIs, but general data equality plus direct return identity could miss nested aliases. Two deliberately faulty public-API witnesses reproduced this gap against the saved v7 worker: returning an action's result array directly, and attaching the input checkpoint to the same error when the first remaining item fails. Both have correct snapshots and unchanged inputs. Both passed their prior observation plans and fail with the v8 nested-reference expectation. This comparison concerns those two witnesses, not the entire v7 suite or an unseen defect rate.

Worker v8 adds data-only `referencePairs`, captured own-data traversal, and exact ordered `referenceIdentity` observations. The host approves selectors and keeps expected results outside the guest. Getters and tracked proxies abstain; missing fields and primitives never count as object aliases, so a negative identity expectation must accompany value/shape expectations. Selectors do not capture pre-call handles or preserve cross-case live references. Protocol and independent-comparison versions changed; old observations cannot be reused as v8 evidence. Resource ceilings and completion authority did not change.

A further equivalent checkpoint implementation used `Object.defineProperty` to attach non-enumerable own data. The preliminary v8 image falsely reported this as missing checkpoint data, despite 587/587 preceding development checks passing. The retained probe reproduces that false rejection. V8 now captures custom own error data regardless of enumerability, while excluding non-enumerable native message/stack diagnostics. Hidden custom accessors abstain without being invoked. A third equivalent checkpoint implementation exercises the complete selected recovery family, including actual data transfer after reset. This is why a passing development suite alone does not establish verifier adequacy.

## Research comparison and adoption

- EvalPlus expanded HumanEval tests 80-fold and evaluated 26 models; its authors report previously missed incorrect programs and pass@k reductions up to 19.3–28.9%. This motivates testing the verifier itself with valid alternatives and plausible defects. Those are the paper's measurements, not Piagent results. We have not installed its generator or copied its datasets. [EvalPlus paper, v3](https://arxiv.org/abs/2305.01210v3).
- fast-check describes command-based histories, a simplified model rather than a copy of the implementation, and replay/shrinking metadata. We adopt the separation between literal behavioral expectations and executed implementations, and retain actual observation histories across a reset. These families currently use finite, authored histories: randomized generation, shrinking and fast-check integration are **not** implemented by this change. [Model-based testing](https://fast-check.dev/docs/advanced/model-based-testing/).
- Stryker separates survived, killed, uncovered, timeout and invalid mutants, and includes timeout in its detected metric. We deliberately do not import that last convention into an agent repair authority: the qualification tests require `fail` with a concrete observed counterexample. Backend errors, unsupported behavior and resource stops remain different outcomes and do not prove a source defect. No Stryker score is claimed. [Mutant states and metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

## Reusable contracts, not benchmark-specific core rules

Six additions live with the Node/TypeScript profile as static, data-only family definitions. Their 137 cases cover bounded retry with injected sleep, partial checkpoint resume, four-layer configuration, workflow-message state, stale search and epoch request lifecycle. The existing three-layer configuration remains version 1; four layers explicitly select version 2. The retry/checkpoint/reducer APIs are preserved instead of being translated into the older accumulator example. Existing library entries are unchanged.

Templates bind exact criterion text/hash, explicit version, parameters, source path and optional dependency list. The installed selection command previews without authority; a separate explicit approval authenticates the expanded checks and selection identity. An altered nested-reference expectation invalidates that signature. Installed library changes invalidate prior verifier binding. Current project verification, source/Git binding, finite repair policy and unselected completion obligations remain separate gates.

The author's public witness builders are under `tests/helpers/production-family-*` and `production-reducer-cases.mjs`. The installed library does not import them or run generators. Test programs contain two equivalent implementations per API, the unchanged exposed faulty fixture, and 18 deliberate mutants. No program's output supplies an expected answer. This still needs independent semantic review: alternatives and mutants authored by the same developer do not establish an unbiased oracle.

## Qualification and limits

The first integration run exposed two test-authoring errors: synchronous callbacks were given Promise settlement trace events, and a deliberately invalid parameter test mutated the parameter object reused by later tests. The parser correctly rejected those inputs. The correction removes impossible sync settlement events and isolates each recipe's parameters; it does not relax parser or completion checks. The initial failed log is retained, including its visible missing-environment skip. A follow-up run exposed a missing Git baseline in the temporary CLI execution fixture; snapshot binding correctly refused it. The fixture now initializes its own local repository instead of bypassing source identity.

Verification covers the installed select/approve path, exact signed checks, captured-source execution, durable reopening and plan drift, and a shallow project-verifier pass that must not hide a nested alias defect. Evidence logs record exact image and source identities outside the repository. Development passing counts are not independent held-out results, 108 model sessions, a measured token saving or a guarantee of arbitrary JavaScript behavior.

Out of scope: real default timers, network/IO/package resolution, arbitrary prototype/accessor graphs, persistence transactions, exhaustive event streams, automatic natural-language requirement matching and universal functional correctness. In particular, current project tests remain required for Node-specific compatibility. Full offline qualification and the independent custodian-controlled release evaluation are separate pending gates; a paid campaign must not be opened or resumed merely because these development checks pass.
