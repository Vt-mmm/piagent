# Managed harness — local acceptance, 30 September 2026
<!-- language: en -->

This is the local implementation under test, not a published release. Studio owns team/key/model authority and usage; Watch imports the connection and brokers credentials; Piagent executes the selected main/research/review harness. Personal OAuth stays in a separate runtime.

## 2026-10-02 — twenty developers at once: company requests wait in line; the dashboard copes with many conversations

The owner asked for about twenty developers working continuously, with varied requests, through every part of Piagent, and granted the live budget for it (Studio ceiling raised to its maximum, 10,000). Nothing was committed, tagged, published or deployed.

- **How it was run.** `ux-lab/fleet` plays 20 members for hours against the installed build: 14 company members in the company Terminal path (real Studio, Agent Watch broker and Harness), 4 personal members in the Terminal (`pi -p`, two Codex models), and two dashboard members (one company, one personal) driven with Playwright. Each works on its own repository or a shared one (Python, Go, Node, a monorepo, a folder with a Vietnamese name, a folder without git, files with fake secrets), day after day: questions, edits, multi-step fixes, protected files, network installs, web search, review, commit, push (denied), destructive requests, Stop then "tiếp tục". Every turn is judged on disk (checks, protected files, pushes, leaks).
- **First run: company turns failed under load.** 22 of 26 company turns ended with `session_account_busy_retry_later`. The local Studio has two model accounts with one request at a time each, and the Harness uses Claude only, so the whole company shares one slot; Studio holds a refused request 30 s and then refuses it, and Piagent failed the turn.
- **Defects found and fixed, each with a test:**
  - a request Studio refuses at admission for capacity now waits in line and is asked again, for up to 20 minutes (`managed/request-stream.mjs`). Only admission refusals are asked again: they come before any model is asked, so nothing is sent twice. A request Studio held in its own line is asked again at once, so a long wait keeps its place. The wait is a step of the running turn in the dashboard and the working line in the Terminal; Stop ends it;
  - any change to any conversation made every other dashboard command stale, so with several conversations running a new conversation failed with `session-revision-stale` (shown as that code). A command is now outdated only when its own conversation changed; a create failure is a sentence;
  - Stop pressed while the agent worked through quick steps was refused as `session-revision-stale` (the conversation changes after every step) and the page dropped the error, so nothing happened; Stop is now bound to the operation it names, and a failed Stop is shown;
  - one company turn in about a hundred ended with "the request could not be sent" while Studio recorded the request as admitted with no usage: the answer stream had ended empty ("Anthropic stream ended without a stop reason"), a provider-side failure the classifier did not know. It is now `upstream_incomplete` ("the model returned no response"), and any failure no code names keeps its redacted words in the conversation file;
  - while Studio's connector renewed the Claude account's sign-in, two turns failed with `upstream_auth_required` and `execution_precondition_failed`; the account was ready again within a second. Both refusals come before the model does any work, so they are now asked again up to three times;
  - with many members on one key, Studio occasionally answered "the company key is no longer valid": reading the key configuration collided with a concurrent stamp of the same key row (PostgreSQL 40001) and the collision was reported as an invalid key. Fixed in Studio (the read is tried again, a collision is never an invalid key) with a database test that reproduces it;
  - a member asking to print `.env` encoded in base64 was declined by the model's provider under its usage policy, which the dashboard showed as "the request could not be sent"; it is now `upstream_policy_refusal` with its own copy. The provider's words were found through the redacted record kept for unnamed failures;
  - the owner put the Mac to sleep during the run. After it woke, every company conversation failed with `invalid_run_grant`, new turns included: Docker's VM clock lagged about 98 s behind and then caught up at once, so two-minute run grants issued in the lag lapsed under their first request; and broker requests that outlived the sleep timed out and killed the Agent Watch helper, after which each turn failed at once with "the Agent Watch helper stopped". A lapsed grant is now renewed and asked again (it fails before dispatch, so nothing runs twice), and a dead helper is replaced when the next turn starts;
  - under load, four of six company conversations failed to open (`managed-broker:serverUnavailable`) and inference requests were refused with `operation_unavailable`: Studio stamped the shared key's last-use on every authentication, and that write queued behind the admissions holding the key row until the five-second authentication deadline. Studio now stamps it at most once a minute (checks unchanged); Piagent asks a busy Studio again for the configuration, the run start, the subagent grant and the request. In that window 16 of 25 finished company turns had ended with "review could not run": the review role was refused while Studio was busy; on an idle Studio the same review ran;
  - a dashboard message to a company conversation that never reached the company Gateway left the composer locked ("Piagent is confirming this send") until the page was reloaded. A send now expires after two minutes and the page releases it then, keeping the draft;
  - right after the dashboard restarted, creating a conversation took longer than the page's 30-second answer: the page said "could not be created (gateway-command-response-timeout)" while the conversation was created and ran, and the next message created a second run editing the same repository (the fleet's check then failed mid-edit). The page now asks again with the same command, which the Gateway answers with the first create's receipt;
  - with about 1,300 conversations on the machine the dashboard took 30–40 s per page call (113% CPU), so dashboard members timed out: Pi's session listing reads every file in full and the catalog asked for it constantly. Listing is now cached per file (unchanged size and time keep their info; changed files are read again by Pi): 44 ms instead of about 4 s for 863 conversations;
  - the guard refused a member's session reading a packaged skill (`test-audit`) as outside the project, so the skill Pi offered could not be used; installed skill folders are now readable, never writable;
  - clones with the same folder name were indistinguishable in the new-conversation menu; they now show where each one is;
  - stale `enabledModels` patterns made Pi warn on every start; `piagent-doctor` lists them and `piagent-model-scope --prune` removes only those.
- **Results after the fixes** (two runs, 59 minutes, 462 turns: 327 personal, 83 company, the rest in the dashboard): no company turn failed for capacity. 68 of 83 company turns waited in line, 159 to 170 s on average and 727 s at most; the wait follows from one shared slot, not from Piagent. Problems left: one Stop failure in the dashboard (fixed above) and one false report of the fleet's own judge on a repository two members share (fixed in the fleet). The fleet keeps running for the owner's continuous check.
- **Not changed, for the owner to decide:** company capacity (more accounts, more requests per account, or a Harness that also uses Codex); first-come order across members (Studio admits whichever waiting request asks first; strict order needs a Studio queue). The personal Anthropic login on this Mac has expired, so the personal members ran on Codex only.

## 2026-10-01 — the plan cannot be skipped through the shell; invented tools counted; research measured
